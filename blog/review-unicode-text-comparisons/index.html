Review Unicode Text Differences Before Merging AI-Cleaned Data

Two text values can look similar while containing different Unicode code points. A cleanup step can also make two different inputs compare equal without establishing that their records describe the same business entity. That distinction matters when an AI assistant proposes a merged list, a standardized customer name or a cleaned identifier. Start by identifying what the field means and what comparison is intended. Do not let a tidy display or a successful text transformation become the entire basis for a record-merging decision.

This guide uses eight original fictional string pairs with manually specified expectations. They are teaching inputs, not actual customer records, observed model outputs or results from a production import. The local checks use Python 3.12.14 and its Unicode database version 15.0.0. The linked Unicode normalization annex provides broader conceptual context; the checks do not claim implementation of a newer Unicode version, full conformance testing, identity verification, confusable detection, security protection or permission to modify records. No executable utility is supplied.

Name the comparison before changing the text

Exact string equality asks whether the sequences being compared contain the same characters in the same order. A normalized comparison asks whether specified transformations produce equal results. A business duplicate decision asks whether records should be treated as referring to the same relevant thing. These questions can be related, but they are not interchangeable. A text comparison can identify a candidate for review without supplying the evidence needed to merge, delete or overwrite a record.

Define the field's role. A display label, a source identifier, a personal name and a free-text note can tolerate different transformations. Changing a display label for a search view does not necessarily justify changing the original identifier. If an integration uses that identifier to address a record, removing a distinction may affect a later action. The linked integration guide covers those separate input-and-effect questions. Here the focus is the text comparison that happens before any such effect.

Keep a copy of the original value alongside a derived comparison value. Record the transformation and its order rather than calling the result clean text. That description should be specific enough for another person to reproduce the comparison. For example, NFC normalization and NFKC normalization followed by Python casefold are different procedures. Neither label means remove every invisible difference or discover the correct business identity. A proposed cleanup rule needs a purpose beyond making a table appear uniform.

Understand canonical and compatibility normalization

Unicode Standard Annex 15 distinguishes canonical equivalence from compatibility equivalence and describes normalization forms based on those relationships. NFC uses canonical normalization, while NFKC additionally applies compatibility mappings. The annex cautions that compatibility normalization can remove distinctions that matter to text meaning. This is useful context for choosing a comparison, not a universal instruction to apply the broadest available transformation to every field in a business dataset.

Python's unicodedata documentation describes its normalize function and the available NFC, NFD, NFKC and NFKD forms. The teaching fixture compares NFC and NFKC rather than implementing the normalization algorithm itself. It then examines a separately named two-step pipeline: NFKC followed by Python str.casefold. That pipeline is stated literally. It is not presented as the standardized NFKC_Casefold identifier operation or as a complete Unicode identifier profile.

Case folding addresses another comparison question. Python documents casefold as intended for caseless matching and more aggressive than ordinary lowercasing. Combining it with normalization can produce additional equalities in the supplied examples. Whether those equalities are desirable depends on the field and task. Keep the operation explicit, and do not interpret a broader comparison key as a recommendation to rewrite people's names or merge their records.

Case A: one accented letter can have different representations

Fictional pair A compares a single precomposed lowercase e with acute accent, U+00E9, with the sequence U+0065 followed by U+0301. The second sequence is a lowercase e followed by a combining acute accent. The original strings are not exactly equal as code-point sequences. Under the local fixture's NFC comparison, they become equal. They also compare equal under the two broader comparison procedures used in the worksheet.

The code-point labels are important because a visual display may not make the difference apparent. One input has one code point and the other has two. Counting code points is not the same as counting user-perceived characters or measuring how much space text occupies on screen. This guide does not provide a general grapheme-segmentation method. It uses the explicit sequence labels to make this particular representation difference inspectable without relying on a font's appearance.

If these strings appear as display text in a proposed AI-cleaned table, canonical comparison can help explain why an exact-text check found a difference. It still does not establish that two complete records are duplicates. A matching label may occur on different records for legitimate reasons. Preserve the source record references and the original values so the representation question can be resolved separately from the business relationship between the records.

Case B: compatibility normalization can remove a width distinction

Fictional pair B compares fullwidth Latin capital A, U+FF21, with ordinary Latin capital A, U+0041. In the stated fixture, NFC leaves the pair unequal, while NFKC produces equal comparison values. NFKC followed by casefold also produces equal values. This difference demonstrates why replacing an NFC rule with an NFKC rule changes the comparison being performed, even when both results are described casually as normalized text.

A proposed cleanup should explain whether the width distinction is intentionally ignored for this field. The answer cannot come solely from the fact that a library can produce a shared value. A display-oriented search key may have a different purpose from the original source text or an external identifier. If the comparison key is used to gather candidates, keep it labeled as derived rather than presenting it as the authoritative replacement for the original field.

Do not assume the transformation is reversible. When distinct originals produce the same comparison value, that value alone cannot tell a later reader which original was supplied. Retaining the source prevents a convenient comparison from erasing evidence needed for another task. This case illustrates information loss under a declared transformation; it does not establish that width differences are always significant or always insignificant in actual business data.

Case C: a ligature and two letters can share a compatibility result

Fictional pair C compares the fi ligature, U+FB01, with the two-character sequence U+0066 U+0069. The local expectations are unequal under exact comparison and NFC, equal under NFKC and under the named NFKC-then-casefold pipeline. As with the width example, the transformation can remove a distinction present in the original input. The fixture is deliberately small so that each operation's result can be compared with an independently written expectation.

A reviewer should ask what an AI-generated explanation claims happened. Saying that the values compare equal after the declared compatibility normalization is a bounded statement. Saying that the original text was identical is a different and incorrect statement for this pair. Saying that two underlying organizations are the same would require evidence beyond either string. Good review keeps those claims separate rather than allowing a fluent summary to slide from one to the next.

This matters when a cleaned export is handed to another person. If only the transformed value remains, the next reader may not know that two different originals entered the process. Include the original source reference and the named comparison procedure in the handoff. That makes the comparison reproducible and gives a later decision-maker the option to use a different rule without having to reconstruct text that was discarded.

Case D: not every space-like character is the same input

Fictional pair D compares x, a no-break space U+00A0 and y with x, an ordinary space U+0020 and y. Both strings contain three code points, but the middle code point differs. In this fixture, NFC leaves the pair unequal and NFKC makes it equal. The named casefold pipeline does not add a further distinction for this pair. A visual review alone is a weak way to identify which space was actually supplied.

Keep the question limited to the specified character. This result does not mean that normalization trims outer whitespace, collapses repeated spaces or removes every separator. Those are different possible operations with their own consequences. If an AI proposes to normalize whitespace, ask which characters it will transform and what it will preserve. A broad label can hide several separate rules that were never selected for the intended field.

For a business handoff, retain an inspectable representation when a spacing difference matters. A code-point sequence or an escaped teaching fixture can make the distinction visible without replacing the original text. Do not infer that a spacing difference is necessarily a typo or proof of a duplicate. The fixture establishes the comparison result under stated operations, while the reason the source contains that character remains outside the supplied evidence.

Case E: case folding is more than ordinary lowercasing

Fictional pair E compares Straße with STRASSE. The source sequence on the left contains U+00DF, the lowercase sharp s. The local fixture leaves the pair unequal under NFC and NFKC. Applying Python casefold after NFKC makes the comparison values equal. Python's documentation uses the sharp-s-to-ss mapping to illustrate why casefold can differ from lowercasing. The example here remains an authored string comparison rather than a language or identity adjudication.

Do not rename the two-step rule case insensitive without retaining its actual definition. That casual phrase can refer to different behaviors in different applications, databases or collations. The worksheet specifies the operations it checks rather than claiming that every tool uses the same equivalence. An actual receiving application's documented behavior would need separate verification before its matching results could be compared with this fixture.

Equal caseless comparison values do not authorize changing the display spelling of a name. A person or organization may have a preferred or authoritative spelling that belongs in the source record. A derived comparison key can serve a search or review purpose while the display field remains unchanged. This separation helps avoid turning a useful candidate-matching technique into an unexamined overwrite rule.

Case F: normalization does not silently trim the value

Fictional pair F compares a value containing ordinary spaces around capital A with a value containing only capital A. The first sequence is U+0020 U+0041 U+0020; the second is U+0041. In the fixture, the pair remains unequal under NFC, NFKC and NFKC followed by casefold. The outer spaces remain part of the transformed strings under those particular procedures.

A trim operation would be another transformation, not a hidden part of the procedures already named. If a proposed task needs trimming, document which characters count and why the field permits that change. Do not add trimming to make a troublesome example pass while continuing to describe the process as the original normalization rule. A changed rule changes the evidence needed to interpret its results.

This is also a useful check on an AI-written explanation. A draft may correctly describe the accented-letter pair and then claim that the same procedure removes extra spaces everywhere. Pair F provides a direct counterexample within the supplied fixture. Reviewing both equality and inequality cases helps reveal an explanation that overgeneralizes a successful transformation. No model generated such an explanation here; the potential mistake is deliberately described as a teaching contrast.

Case G: similar-looking letters need not normalize together

Fictional pair G compares Latin capital A, U+0041, with Cyrillic capital A, U+0410. Their appearance depends on the rendering context, but their code points differ. In the fixture, exact comparison and all three declared transformed comparisons leave them unequal. The result is a statement about these supplied strings and procedures, not a general method for detecting visually confusing identifiers or malicious text.

Do not treat unequal normalized values as proof that records describe different entities. The source text may be wrong, an alternate representation may be intentional or the field may require a different matching design. Those possibilities need their own evidence. Similarly, visual resemblance does not establish equality or authorization to replace a character. Keep the code-point observation separate from a proposed explanation for why it appeared.

This guide does not implement confusable detection, mixed-script policy or a security review. Those are distinct requirements. Its useful contribution is narrower: normalization is not a universal operation that turns anything resembling the same letter into one value. A proposed data-cleanup policy should name any additional character or script handling explicitly and evaluate it in the actual authorized context rather than inferring it from the word normalize.

Case H: a joining character is not removed by this pipeline

Fictional pair H compares a, U+200D ZERO WIDTH JOINER and b with the two-letter sequence ab. In the local fixture, the pair remains unequal under all three declared procedures. The joining character is still present in the transformed left value. Its visual presentation is not the evidence used for this result; the fixture preserves the actual character sequence and provides code-point labels for inspection.

Do not extend the example into a recommendation to delete joining or other format characters. Such characters can have meaningful roles in text, and this guide supplies no general removal policy. If an application's identifier contract excludes a particular character, that is a separate documented condition to inspect. A generic cleanup instruction should not silently turn a comparison question into a deletion rule across arbitrary text.

The handoff should state the actual limit: these operations did not remove the supplied joining character. It should not claim that all invisible characters are preserved or removed, that the text is safe, or that the records are unrelated. A precise limitation is more useful than an expansive promise about sanitization because it tells the next reviewer what remains unexamined.

Use transformed equality as evidence for a bounded next decision

A candidate-review table can retain source record identifiers, original strings, derived comparison keys and the rule that produced them. If two keys collide, keep the separate originals visible. A collision means that the declared transformation produced equal values; it does not resolve every field needed for a merge. The business must define what additional evidence and authorization its actual record decision requires.

Keep serialization and parsing separate from normalization. The existing CSV handoff guide owns preservation of text through a file boundary. The JSON duplicate-name guide owns repeated decoded names within object scope and explicitly does not normalize names. This guide addresses a different comparison question after strings are available. Applying a new normalization rule to JSON member names before checking uniqueness could create a different contract and needs its own deliberate design rather than an implied extension of that earlier guide.

If an AI assistant proposes a cleanup, ask it to state the original, the exact transformation and the intended effect separately. Compare a proposed explanation with both the equal and unequal fixture cases. Preserve uncertainty about business identity and do not describe a draft merge list as an executed change. The separate integration and approval processes govern any actual effect. This guide contains no record writes, network integration or permission decision.

Frequently asked questions

Does equal normalized text establish that two records are duplicates?

No. It establishes equality under the named text transformation. A business duplicate decision needs an appropriate field definition, supporting evidence and authorization. Distinct records can share labels, while different text can refer to the same thing for reasons outside this fixture. Keep original values and source references available for that separate decision.

Are NFC and NFKC interchangeable cleanup rules?

They produce different results in the supplied width, ligature and no-break-space examples. NFKC applies compatibility mappings that can remove distinctions retained by NFC. Choose a rule for the actual field and purpose rather than assuming that a broader transformation is always preferable. The fixture demonstrates results; it does not recommend a universal rewrite policy.

Does the named pipeline implement standardized NFKC_Casefold?

No such conformance claim is made. The fixture literally applies Python NFKC normalization and then Python str.casefold, with no additional normalization step. That is the procedure being checked and named here. Standardized identifier profiles, arbitrary input handling and receiving-application behavior are separate questions requiring their own specifications and verification.

Will normalization remove surrounding spaces and joining characters?

The declared procedures do neither in fictional pairs F and H. Those examples preserve the supplied outer ordinary spaces and U+200D joining character. Trimming or deleting characters would add separate rules. Do not infer a general sanitization or security property from a normalization result, and do not silently change the procedure to make a particular case equal.

Are the equality totals measurements of AI accuracy?

No. The eight pairs and expected results are deliberately authored teaching material. Local Python checks matched the manually specified expectations, but no model, client dataset or production import was run. The counts describe this fixture only. They do not measure duplicate-detection quality, language correctness, user experience or the suitability of a business merge policy.

What should a reproducible comparison handoff retain?

Keep original values, source record references, the named operations in order, runtime and Unicode database versions, derived results and unresolved business decisions. The supplied files make the character sequences and expectations inspectable. They are not an executable utility, a replacement parser, a confusable detector, a security certification or authorization to overwrite records.
